## 1. 結論

v1.0 は **無料アプリ**として出す。課金・AI生成・テンプレート・プッシュ通知は v1.0 に入れない。
公開に必要なものは次の3種類だけで、下の Step 0 → Step 8 を上から順に消化すれば審査提出に到達する。

1. **コア体験**（リスト作成・編集・チェック → 家族招待・共有 → オフライン復帰）
2. **審査必須要件**（アカウント削除、プライバシーポリシー、App Privacy 申告、プライバシーマニフェスト、レビュアー用デモアカウント）
3. **運用最低限**（Crashlytics、Analytics、TestFlight 実機検証）

分岐や「余裕があれば」は本書に置かない。書いてあるものは全部やる。書いていないものは v1.0 ではやらない。

## 2. v1.0 スコープ確定

### 2.1 v1.0 に入れる

| 領域 | 内容 |
|---|---|
| 認証 | Sign in with Apple / Google / メールOTP（実装済み） |
| リスト | 3種別の作成・編集、項目の高速追加・編集・チェック・削除、30日復元、複製 |
| 共有 | リンク招待（OS共有シート）、受諾、リアルタイム反映、メンバー削除・退出・所有権移譲 |
| オフライン | キャッシュ読み込み、オフライン書込、復帰後同期、オフラインBanner、Last Write Wins + 削除優先 |
| 設定 | プロフィール、日英切替、認証方法、規約・プライバシー・問い合わせ、バージョン、ログアウト |
| アカウント削除 | アプリ内完結、所有リストの移譲/削除解決、7日猶予と取消、Apple トークン失効 |
| 監視 | Analytics 主要ファネル、Crashlytics |
| Free上限 | 3リスト / マイテンプレート1件の上限は**維持する**（理由は 9章） |

### 2.2 v1.0 から外す（v1.1 以降）

| 外すもの | 元チケット | 外して問題ない理由 |
|---|---|---|
| RevenueCat 課金一式 | PAY-001〜005 | 無料アプリなら App Store Connect の課金設定・Sandbox検証・Webhook が丸ごと不要。審査項目も減る |
| AIリスト生成 | AI-001〜005 | コア価値ではない。OpenAI の費用・安全審査・評価セットが公開のクリティカルパスから外れる |
| 公式/マイテンプレート | TMPL-001〜004 | seed データ整備と日英テンプレート文言が丸ごと不要になる |
| プッシュ通知 | NOTIF-001〜003 | Push capability・APNs鍵・通知許可UX・集約jobが不要。共有はリアルタイム購読で成立する |
| 手動並べ替え・検索・数量解析 | LIST-005 | 高速追加とチェックが動けばコア体験は成立する |
| アーカイブ | LIST-006 の一部 | 論理削除+30日復元で代替できる |
| メール招待・QR招待 | SHARE-003 の一部 | OS共有シートのリンク招待だけで招待は完結する |
| 手動の競合比較UI | OFF-002 の一部 | Last Write Wins + 削除優先 + 入力内容コピーで審査・実用に耐える |
| Android・Web | - | 元々 Phase 1 スコープ外 |

`react-native-purchases` は依存に残るが、**v1.0 では SDK を初期化しない**。App Store Connect にも課金アイテムを登録しない。

### 2.3 削ってはいけないもの

以下は「最短公開」でも削減対象にしない。削ると審査で確実に落ちるか、公開後の作り直しが発生する。

- アプリ内のアカウント削除（Guideline 5.1.1(v)）と Sign in with Apple トークン失効
- プライバシーポリシー・サポートURL の実在するページ
- App Privacy 回答とプライバシーマニフェスト（`PrivacyInfo.xcprivacy`）
- レビュアーがログインできるデモアカウント
- Security Rules による権限保護（Emulator テストつき）
- Free上限の原子的判定（後から入れると既存データの読み取り専用化が必要になる）

## 4. 一直線のステップ

各 Step は上から順に実施する。**ゲートを満たさないまま次の Step へ進まない。** WIP は常に1チケット。

### Step 0 — 外部の待ち時間を先に消す（11h / 待ち時間 最大3日）

コードを書かなくても進む作業で、かつ DNS 反映やドメイン検証の待ちがある。Step 1 と同じ週に着手し、待っている間に Step 1 を進める。

| ID | 内容 | 工数 | 完了条件 |
|---|---|---:|---|
| EXT-001 | App Store Connect にアプリレコードを作成する。App ID `com.soroe.app`、Capabilities は Sign in with Apple と Associated Domains のみ有効化（Push と In-App Purchase は無効のまま） | 1h | App Store Connect にアプリが存在し、Xcode/EAS から見えている |
| EXT-002 | 取得済み独自ドメインを Firebase Hosting へ接続し、`/.well-known/apple-app-site-association` を配信する。`app.config.ts` の `applinks:soroe.app` と Android intentFilter の host を実ドメインへ差し替える | 3h | 実機で招待URLをタップしてアプリが開く。AASA が `Content-Type: application/json`、リダイレクトなしで返る |
| EXT-003 | 利用規約・プライバシーポリシー・サポートページを同ドメインで公開する。Analytics/Crashlytics が収集する項目、OTPメールの用途、アカウント削除手順を明記する | 3h | 3つのURLが公開され、アプリの設定画面から開ける |
| EXT-004 | OTP 送信用のメールプロバイダ（Resend 等）を契約し、送信ドメインの SPF/DKIM/DMARC を認証、From アドレスと問い合わせ受信先を確定する | 1h | プロバイダ管理画面で送信ドメインが Verified。**DNS 反映に最大48時間かかるので最初にやる** |
| MAIL-001 | `EmailProvider` の実装をコンソール出力から実プロバイダへ差し替える。API キーは Functions Secret、送信失敗時の扱いとバウンス確認まで含む | 3h | 本番 Functions から実際にOTPメールが届き、`requestEmailOtp` のレート制限テストが通る |

**ゲート G0**: 実ドメインで招待リンクが開き、規約・プライバシー・サポートの3URLが公開され、実機に本物のOTPメールが届く。

### Step 2 — 共有を成立させる（24h）

v1.0 の価値の中心。ここが動けば「出せるアプリ」になる。

| ID | 内容 | 工数 | 完了条件 |
|---|---|---:|---|
| SHARE-001 | `members` とユーザー側一覧参照、owner/editor の Security Rules。追加と一覧参照作成は原子的・冪等 | 6h | Emulator で owner/editor/非メンバーの読み書きを網羅したテストが通る |
| SHARE-002 | `createInvite` / `acceptInvite` / 取消。乱数+ハッシュトークン、期限7日、requestId冪等、既参加・自己招待・削除済み・Free上限の検証 | 7h | 全異常系のユニットテストが通る |

## 6. 審査で落ちやすい箇所と対策

| Guideline | リスク | 本ロードマップでの対策 |
|---|---|---|
| 5.1.1(v) アカウント削除 | アカウント作成できるのにアプリ内削除がない | Step 4 の DEL-001。削除導線は設定画面の上位階層に置く |
| 2.1 完全な機能 | レビュアーがログインできず「機能が確認できない」 | Step 7 の REVIEW-001（固定OTP allowlist）と審査メモのデモ招待リンク |
| 4.8 ログインサービス | 他社ログインを提供するのに Sign in with Apple がない | 実装済み（AUTH-002）。ログイン画面での並び順も確認する |
| 5.1.1 プライバシー | プライバシーポリシーURLが無効、App Privacy 回答と実態が不一致 | Step 0 の EXT-003、Step 7 の REL-003。Analytics/Crashlytics の収集を正直に申告する |
| — プライバシーマニフェスト | `PrivacyInfo.xcprivacy` 未添付でビルド提出が警告/拒否 | Step 7 の REL-003 |
| 2.3 正確なメタデータ | 未実装機能（AI・課金・テンプレート）をスクリーンショットや説明文に書く | v1.0 の説明文からAI・課金・テンプレートの記述を全部落とす。「近日提供」も書かない |
| 3.1.1 App内課金 | 課金がないのに IAP capability が有効 | EXT-001 で In-App Purchase を無効のままにし、RevenueCat SDK を初期化しない |
| 5.1.2 データ共有 | リスト名・項目名・メールアドレスをログや分析へ送っている | OBS-001 の「個人情報を送らないテスト」で機械的に担保 |
| 1.2 ユーザー生成コンテンツ | 共有機能に通報/ブロックがない | v1.0 の共有は**招待した相手だけ**の閉じた共有であり、公開UGCではない。審査メモに1行書く |

## 7. 提出直前チェックリスト

## 9. 決めておく論点（推奨つき）

### 9.1 Free上限を v1.0 でどう扱うか

**推奨: 3リスト / マイテンプレート1件の上限を維持する。**

無制限で公開してから v1.1 で課金と上限を入れると、既存ユーザーの超過データを「選択式で読み取り専用にする」処理（PAY-004 相当、約5h）と、機能を取り上げる説明が必要になる。上限を最初から維持すれば、v1.1 は「Premium で上限が解放される」という増加のみの変更になる。

上限到達時の文言は「現在は3つまで作成できます」に留め、**「Premium で近日解放」等の未提供機能の予告は書かない**（Guideline 2.3 に触れる）。

### 9.2 招待リンクのドメイン

`app.config.ts` の `applinks:soroe.app` と Android intentFilter は現在プレースホルダ。EXT-002 で実ドメインへ差し替える際、**取得済みの実ドメイン名を確定**する必要がある。規約・プライバシー・サポート・OTP送信元も同じドメインへ揃える。

### 9.3 v1.1 の順番（参考）

公開後は次の順で戻る。v1.0 で外したものは仕様書ごと消していないので、`soroe-implementation-backlog.md` のチケットをそのまま使える。

1. PAY-001〜005（課金）— 収益化と Free上限の意味づけ
2. TMPL-001〜004（テンプレート）— 課金価値の裏付け
3. NOTIF-001〜003（通知）— 共有の再訪導線
4. AI-001〜005（AI生成）— 差別化
5. LIST-005（並べ替え・検索）、AUTH-006 の細部
