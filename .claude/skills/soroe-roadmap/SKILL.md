# Soroe ロードマップ進行

v1.0（無料アプリ）を App Store で公開するまでの残り29チケットを、迷いなく1件ずつ完了させるための手順。

このリポジトリの資料は合計3,000行を超える。毎回全部読み直すのが最大の時間の無駄なので、**チケット単位で読む範囲を絞る**ことがこのスキルの中心にある。

## まず現在地を出す

会話の最初に必ず実行する。git のコミット履歴だけを見て現在地を判定するので、別途の進捗ファイルと食い違うことがない。

```bash
bash .claude/skills/soroe-roadmap/scripts/status.sh
```

完了済みチケット、次に着手すべきチケット、そのStepのゲート、未コミットの変更が出る。ここを起点にする。

ユーザーが特定のチケットを指定した場合でも一度実行する。依存が未完了のまま着手すると手戻りになるため。

## 1チケットの進め方

WIPは常に1件。着手中のチケットを完了させてから次へ進む。以下の5段階を飛ばさない。

### Phase 1 — 着手判定（Definition of Ready）

`references/tickets.md` の該当チケット1行を読む。ここに依存・工数・参照すべき資料の箇所・完了条件がまとまっている。

着手してよいのは次を全部満たすときだけ：

- 依存チケットが完了している（status.sh の出力で確認）
- 外部サービス側の作業（Apple、DNS、メールプロバイダ）が必要なら、それが先に済んでいる
- 入出力・権限・オンライン必須かどうかが決まっている
- 見積が8hを超えそうなら、着手前に分割する

満たさないものがあれば、**着手せずにユーザーへ何が足りないかを伝える**。ここで止めるのが結局いちばん速い。

### Phase 2 — 読む範囲を絞る

`references/tickets.md` の「参照」列に書かれた箇所**だけ**を読む。仕様書や設計書の全文は読まない。行番号つきで指定してあるので `sed -n '199,229p' docs/soroe-functional-specification.md` のように部分読みする。

加えて、そのチケットに関係する不変条件を `references/constraints.md` で確認する。ここに書かれているものは、破ると後から作り直しになるものだけを集めてある。

Expo / React Native Firebase の API を新しく使う場合は、記憶で書かずに https://docs.expo.dev/versions/v57.0.0/ の該当ページを確認する（`apps/mobile/AGENTS.md` の指示）。Expo は破壊的変更が多く、古い書き方で書くと実機ビルドまで気づけない。

### Phase 3 — 計画を書く

`docs/superpowers/plans/<YYYY-MM-DD>-<ticket-id小文字>-<slug>.md` に計画を置く。既存の `2026-07-30-list-002-create-and-list-index.md` が書式の見本になる（Goal / Architecture / Tech Stack / Global Constraints / Task N + チェックボックス手順）。

計画が3タスク以下に収まるほど小さいチケットなら、計画ファイルは省いてよい。逆に7タスクを超えるなら、そのチケットは分割すべきというサイン。

### Phase 4 — 実装

このリポジトリの層構造とテスト慣習は `references/constraints.md` にまとめてある。特に効くのは次の3点：

- スキーマ（`packages/shared`）と Functions の handler 層は**テストを先に書く**
- Firestore を直接叩く store 層と `app/` 配下の route component は単体テスト対象外（既存慣習）。代わりに Emulator + 実機で確認する
- Security Rules を変えたら `functions/src/rules/firestore.rules.test.ts` に必ずケースを足す

### Phase 5 — 完了判定と記録

```bash
pnpm run ci && pnpm --filter functions run test:rules
```

これに加えて `references/verification.md` のチェックを実施する。画面チケットなら状態網羅（通常・空・読込・エラー・無効・オフライン）、a11y、i18n、PIIをログへ送っていないことを確認する。ここは審査とユーザー体験に直結するので省かない。

完了したらコミットする。**メッセージの先頭は必ずチケットIDにする**。status.sh がこれを読んで進捗を判定するため、ここが崩れると現在地がわからなくなる。

```
LIST-003: リスト詳細の購読と項目の高速追加・チェックを実装
```

外部作業（EXT-001〜004 のようにコードを書かないもの）も、`docs/` に完了記録を1〜数行書いてから同じ書式でコミットする。`docs/spike-001-offline-sync.md` と `docs/firebase-deploy.md` が前例。記録がないと、後日「DNS認証は済んでいたか」を思い出せない。

ゲートチケット（SHARE-005 / OFF-003 / DEL-002）は、`docs/soroe-functional-specification.md` の該当する受け入れ条件（AC-01 / AC-03 / AC-07）に検証結果を追記してからコミットする。

## Stepのゲート

Step内の全チケットが終わっても、ゲートを満たさなければ次のStepへ進まない。ゲートは「動くはずだ」ではなく実機で確かめる。

| Step | ゲート |
|---|---|
| 0 外部準備 | 実ドメインで招待リンクが開き、規約・プライバシー・サポートの3URLが公開され、実機に本物のOTPメールが届く |
| 1 リスト | 3種別のリストを作り、項目を追加・編集・完了・削除・復元でき、4件目が上限で拒否される |
| 2 共有 | 実機2台で「作成→招待→受諾→追加→完了→権限喪失」が通る（AC-01） |
| 3 オフライン | 機内モードで操作 → アプリ再起動 → 復帰で別端末へ反映される（AC-03） |
| 4 設定・削除 | Apple / Google / メールの3方式それぞれで、アプリ内だけでアカウント削除が完了する（AC-07） |
| 5 監視 | production ビルドのクラッシュが symbol 付きで Crashlytics に届く |
| 6 品質 | P0/P1 不具合0件、CI緑 |
| 7 TestFlight | 説明なしのテスターがコア体験を完走、クラッシュ0件 |
| 8 提出 | `references/verification.md` の提出直前チェックリストが全部埋まる |

## スコープを守る

v1.0 に**入れないもの**：RevenueCat 課金、AIリスト生成、公式/マイテンプレート、プッシュ通知、手動並べ替え・検索、アーカイブ、メール招待・QR招待、Android・Web、Dark Mode。

実装中に「ついでにこれも」と思いついたら、手を出さずに `docs/soroe-implementation-backlog.md` の該当チケットへ1行メモして戻る。105hの計画が崩れる原因はほぼこれで、1人開発では取り返せない。

ユーザーがスコープ外の機能を明示的に依頼した場合は、それが v1.1 送りである旨と、入れた場合の公開遅延の見込みを1行伝えたうえで、依頼どおり進める。判断はユーザーのもの。

## 参照ファイル

| ファイル | いつ読むか |
|---|---|
| `references/tickets.md` | チケット着手前に該当行。全29チケットの依存・工数・参照箇所・完了条件 |
| `references/constraints.md` | 実装前。破ると作り直しになる不変条件（層の境界、冪等性、権限、PII、a11y、デザイントークン） |
| `references/verification.md` | 完了判定時と提出前。DoDチェック、ゲート記録の書き方、審査必須項目 |

ロードマップ本体は `docs/soroe-app-store-launch-roadmap.md`。スコープや見積の根拠を疑うときだけ開く。日々の進行には上の3ファイルで足りる。
